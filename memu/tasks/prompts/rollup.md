任务：按事项总结材料，生成一个完整视图。view 为 day / month / runtime / memory，
scope 给出范围（某日、某月、某主题、全局）。输出的单位是事项，不是输入记录。

先在内部完成归并，再输出 entries：
1. 通读全部材料，识别不同的目标或问题。同一目标下的提问、回答、尝试、报错、修复、
   验证和追问属于同一事项；换了时间、会话或证据编号也不因此拆成新事项。
2. 归并每个事项的重复内容，按事件时间梳理变化；保留最后明确的决定、实际进展或结果，
   以及仍未解决的问题。不要把“请求执行”写成“已执行”，也不要把助手自述升级为实测。
3. 每个事项只写一条完整的结果摘要：围绕什么目标，推进到了哪里，有什么明确结论或
   待办。只写材料支持的部分；只有请求就写请求，不补造结果或未决问题。
4. 一个事项可引用多条 Unit。facts 合并支撑该摘要的不同阶段和决定的证据，仍只选
   scope.refs 内的引用。不要求每条输入都有一条输出，也不要求穷举所有输入引用。
5. 最后检查事项是否重复、句子是否完整、总长度是否符合预算，再输出 JSON。

day / month 先输出 agenda，再输出 entries。agenda 是事项分组清单，每组包含简短
matter 名称和 refs。必须将 scope.refs 中的每个输入恰好归入一个事项，不能只处理
开头几条。读写文件、安装命令、权限申请等过程应归入其服务的目标，不独立算作事项。
同一个目标中的反复排错与后续决定也要归到一起，不以操作步骤或工具名拆分。
entries 与 agenda 按顺序一一对应；每条正文引用该组中直接支持最新结论和关键变化的
证据即可，不必引用组内全部过程。agenda 只是归并校验信息，不会写入正文。
不同目标不能为了凑条数随意合并；也不要把同一目标拆成多条来填满上限。

例如：多条记录分别讲“要求修复启动失败”“尝试安装依赖”“助手报告修复”“用户要求先
验证再上线”，应合成“排查启动失败；助手报告已修复依赖问题（未独立验证），用户要求
验证通过后再上线。”并引用支撑进展与决定的记录，而不是写四条操作流水账。

通用：
1. 只使用本次提供的材料。
2. 写决定、结果、明确的进展与现行状态；合并重复表达，留下当前任务允许的证据引用。
3. 同一件事的新旧说法，以事件时间晚的为现行状态；旧的留在 Unit 里，
   视图里需要时只用一句话交代变化。
   用户后续纠正也必须纳入。区分不同环境、组件和阶段的结果，不能将局部失败
   概括为全局不可用；未列举的组件不等于被移除，不擅自加“仅剩 / 全部”等限定。
4. 只是提过、试探过、被否决或被取代的内容，不往上带；明确表达的计划保持为计划，
   测试不写成迁移。
5. update 接续有效的旧视图；rebuild 只用本次有效材料重新组织，
   不带回已无依据的旧句子。
6. 返回当前完整视图，不是补丁。
7. 每条结论必须保留其证据中的限定：虚构、示例、假设、尚未发生等都不能省略。
   合并相同事件的重复表达；一条简单事件只写一项，不为填充视图反复改写同一内容。
8. 保留来源身份与证据性质。AI 助手给出的估算、判断或建议，要明确标为助手的回复或建议，
   不提升为用户已采纳、实际部署状态或实测结果。
9. facts 仅从 scope.refs 选择。材料内嵌的 facts 是下一层证据，若未列入 scope.refs，
   不直接跳过去引用；尤其 MEMORY 应引用当前提供的 Runtime 入口。
10. 缺少后续记录不等于否定事实。没有采纳或部署的证据，只能说“记录中未见采纳 / 实测”，
    不得写“未采纳 / 未部署 / 未实测”；后者会把信息缺失变成用户的实际决定或状态。

摘要不是 Unit 的缩写合集。先把同一事项的提问、回答、补充合成一项，抽取目的与结果，
不逐条转述。信息少时更短，不因为额度充足而补充细节。policy.detail 不适用于视图。
scope.max_entries 是输出条数上限，不是已识别的事项数，更不是需要填满的配额。
scope.entry_target_chars（若提供）是单条写作目标；为保留完整事项及关键限定可以超过目标。
scope.entry_chars 是每条 body 的字符上限；scope.total_chars 是全部 body 的字符总预算。
两者都必须遵守；保留完整句子需要余量，通常写得比单条上限更短。
接近上限时重新概括，删去命令、路径、参数和过程细节，不能机械截取前 N 字，
不能在单词、代码、路径或句子中间结束。禁止用省略号代替被截断的结果。
只有一个事项时写一个完整短句，不分成“提问 / 回答 / 补充 / 当前关注”等重复条目。
参数、配置命令、性能数字、方案清单留在 Unit，通过 facts 下钻；
只有数字本身就是用户明确采纳的目标或关键决定时才带上来。

按 view：
- day：按当天事项写做了什么、得到了什么结论、还未决定什么。一项通常 1～2 句，
  以 160 字符以内为写作目标，信息少时更短；为保留完整结果或关键限定可以超过 160。
  单条硬上限为 500 字符，同时遵守 scope 给出的总预算或更紧的上限；同次问答合成一项。
  Unit 按事件时间归日，只知道月份的不安排到某一天。
  问答型材料只概括所咨询的问题、回复性质及明确的后续决定，删去助手答案里的数值和
  方法清单。例如选型咨询记为“咨询服务器选型，收到助手的比较建议，记录中未见选定方案”，
  而不复述各型号参数和价格。没有明确决定时不推测行动。
- month：比日摘要再高一层，按持续方向写本月进展、阶段结果和未决事项，通常一项一句、
  最多 100 字。不要重放每天的动作或复述技术答案；若只有一次咨询，就写本月咨询过哪个
  问题、处于什么阶段，不虚构长期项目或趋势。日摘要只作导航，事实仍引用 Unit。
  月内较早发生、后来才导入的事件，按实际时间纳入。
  单次咨询在月摘要里只留下问题方向与所处阶段，省略具体设备型号和参数；
  只有明确选定或持续采用的对象才保留名称。不要仅删几个字就复制日摘要。
  batch_entries 优先来自已完成的日概述；directions 是可以归纳的事项方向，不是 Runtime
  目录。用方向概括“这段时间推进到哪里”，不复述某天提出了哪个型号的具体问题。
- runtime：一个主题的现状、近期变化和继续读取的入口。项目与事项写进展、约定、
  结果、正在做、完成过；人与用户只写原文明确的信息和偏好，
  不从一次行为概括出人格或关系。
  按 material.topic.description 限定关注范围，合并跨时间的变化，不列实体百科或复述所有问答。
  单次助手建议不能变成现行部署；没有用户确认时保留“咨询中 / 助手建议”。
- memory：简短概要，每项指向下一跳（Runtime 入口，必要时 Unit）。
  body 只写当前关注事项与状态，不复述技术答案、参数、数值或建议清单。
  导航只写在 facts，不在 body 写任何“入口”、目录或主题名列表；目录由程序生成。
  不从 Unit 标签推断存在 Runtime；只可引用 scope.refs 中实际提供的 Runtime 或 Unit。
  长度服从 policy。

day / month 输出 agenda 和 entries；runtime / memory 只输出 entries。
本地 AI 工作记录中的“助手报告（未独立验证）”必须保留这一归属和不确定性；工具创建、启动、完成、验证成功不得互相替代。自动上下文摘要不构成一次新的用户决定。
