任务：把材料整理成可以独立理解、独立检索的 Unit，一条一个时间点、一个核心动作。

1. 普通材料按独立事件或完整子话题切分，粒度服从 policy.detail。默认全写，
   黑名单之外不先判断值不值得。
2. 正文写清谁、对谁或什么、做了、提了或决定了什么。姓名与关键名词写进正文，
   不用只有代词的句子——它要能被 grep 到。
3. 聊天默认记“这次提出 / 说明 / 决定”，用谈话时间；若明确记的是另一件实际发生的事，
   用那件事的时间。“下月停用 A”记成现在的计划，不写成已停用。
   来源是 Agent 的工作记录，就如实记为工作记录，不写成用户原话。
4. 否决、犹豫、未定照实写；措辞本身重要（决定、偏好）时引原话。
5. 有媒体时，把 caption 与随行文字合并写进正文，原媒体放进 facts。
   媒体 item.context 中的摘要属于该媒体的上下文，不是额外的 coverage 输入。
   coverage 的序号只对应 material.items；不要为 context 内的元素新增序号。
   可以引用 supporting_refs 中的摘要和原文定位符，引用摘要时仍须同时引用原媒体。
   随行文字作为独立 item 提供并单独覆盖；若它描述另一件事，可以独立成条，不强行引用图片。
6. facts 选直接支撑这条正文的材料；依据不连续就分别列出，不用大范围包住。
7. topics 只用输入给出的现有跟踪主题规范名，按照其关注范围归类；没有合适的就留空。
   新主题由后续跨记录发现任务统一建立。不要把人名、产品名、型号逐个提成主题。
8. 不同来源记同一件事也各自成条，不因历史里有相似正文而省略。
9. 普通材料已完成黑名单过滤，非空材料必须生成至少一条 Unit，不返回空数组。
   测试、示例、虚构或假设也照实记录其限定，例如“来源提供了一个虚构示例”，
   不把示例中的事件写成现实中已发生的事实，也不因它是示例而直接丢弃。

10. 对话必须区分用户原话、用户引用的第三方内容和 AI 助手回复。
    提问中的引文不是用户本人经历；助手的猜测、建议或推论不提升为已证实事实。
    消息时间只对应这次表达，不能用它替代被讨论事件的发生时间。
    微信等多人聊天按每条消息标注的发言人归属陈述，正文保留其备注或昵称；同名时用
    来源 ID 区分。只有标注“我自己”的消息才归属于来源所有者，不能把其他人的话写成
    所有者的经历或决定。转发者与转发内容中的原发言人分开表述；身份未知时如实保留。
11. 输入 item.source_slice 标明原始记录的字符片段（从 0 开始，start 包含、end 不包含），
    输入 item.body 是材料，输出 units[].body 写事件。messages 给出所属消息的角色和时间；
    不把片段当成整条消息，不补造缺少的前后文。facts 使用 ref。
12. 长十六进制、Base64、checkpoint 等编码数据保留在原始记录中，Unit 记录来源提供、
    讨论或明确解析该数据的事件并引用原文；正文不逐字复制长串，不自行解码或猜测其中事实。

输出 units。

工作日志的特殊规则（仅 material_kind=agent_worklog 时，覆盖上面的逐项记录和最少条数要求）：
把完整工作片段整理为“目标或问题 → 实际修改/决定 → 验证结果与限制”，保留关键文件、参数和结果。
同一工具调用及其返回属于一次动作，不能各生成一条重复记忆。工具返回不是用户发言；
调用参数只证明尝试，成功必须有返回或后续确认。读取文件、目录列表、任务状态通知、
“接下来我要……”等过渡话语属于上下文，不逐条记为事件。被读取文件中的说明和示例不能
提升为本次已完成的工作。尚无实质新增的片段可以用 coverage.ignored=operational_context
说明，不为满足条数编造“提供了一段日志/签名”等记忆。原始素材已保存，不会因此丢失。
粒度是一项可独立理解的工作进展，不是一条日志或一个工具调用。尚未完成的动作留在 memory
等待后续结果；仅包含阅读准备、导航或会话限额通知的批次允许 units=[]。同一目标下连续的
文件查看、结构识别和阅读计划不要分别成条；最终明确的技术判断、实际修改、验证结论才成条。
