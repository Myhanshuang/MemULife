# 架构设计与演进

本文说明当前服务边界、部署设计与后续优化方向。

## 保持的核心边界

| 边界 | 设计理由 |
|---|---|
| acquisition → core | 采集负责发现、授权和选定素材的交付，最终记忆由核心统一校验与提交。 |
| MCP → core | MCP 无状态，不访问记忆文件、数据库或模型；可独立部署与扩容。 |
| 单写入 core | 稳定行号、跨文件发布日志、修订历史和后台任务需要一致的提交顺序。 |
| 文件 + PostgreSQL | 文件保存正文与附件，数据库保存权威控制和索引；恢复必须兼顾两者。 |
| 模型与写入分离 | 模型提出结构化结果；引用、版本、权限、保护和提交由程序校验。 |
| 手动修订与自动重建分离 | 保留用户修订的最终稿，只重建未保护部分及派生索引。 |

持久任务与单写入者共同协调正文、事务和派生视图，服务边界围绕采集、记忆处理与模型访问组织。

## 当前设计

### 完整部署入口

Compose 与 k3s 均包含数据库、初始化、核心、MCP、采集服务和持久卷。初始化阶段注入数据库配置，核心就绪后提供管理与模型访问入口。

### 凭据与数据按角色分离

MCP 仅接收认证和核心连接配置；采集服务接收采集数据库配置，来源凭据保存于自己的私有卷；模型密钥只交给核心。初始化脚本生成新的随机 token 与数据库密码，渲染器不向标准输出打印 Secret。

源码包由显式文件清单构建，并附文件摘要清单与 SHA-256 校验文件。

### 管理服务适应容器和反向代理

管理服务支持独立配置 Host 和 Origin，适应容器与 HTTPS 反向代理。`/readyz` 检查核心依赖，存活与就绪探针不执行模型推理。

### 减少重复协议与重建耦合

页面编辑和外部 MCP 共用修订事务、稳定定位符、保护、幂等和版本历史机制。正文提交完成后，相关索引与视图由持久后台任务更新。

## 后续优化建议

| 优先级 | 优化点 | 实施方向与边界 |
|---|---|---|
| P1 | 采集凭据仍使用进程环境安装 | `SourceCredentials` 在连接探测时临时修改共享环境。后续改为按来源注入显式凭据上下文，并只把该读取器需要的变量交给子进程，减少并发配置相互影响。不要改变“先选择再持久化”边界。 |
| P1 | 采集与核心共用数据库身份 | 入门模板使用专用数据库，生产环境可进一步拆分角色及权限。先明确两类表的所有权和迁移权限，再提供最小权限配置，避免直接换角色导致初始化失败。 |
| P1 | 大仓库管理页的遍历成本 | 对来源、日期、格式和保护状态增加适当的数据库查询路径与分页，减少每次浏览对所有正文的读取。实际正文与编辑版本仍以权威仓库为准。 |
| P2 | 核心服务承担多类协调逻辑 | 在维持单写入者与统一事务的前提下，逐步整理视图调度、删除依赖计划、修订和检索服务接口；优先提取职责清楚的模块，不进行整库重写。 |
| P2 | 部署的版本固定程度 | 后续为发布版本记录镜像 digest、依赖锁定与兼容范围；模型权重版本必须继续显式配置，不能把不同向量空间混用。 |
| P2 | 恢复操作标准化 | 增加配套数据库与卷的离线备份/恢复命令、恢复前一致性检查及简短回执，使用隔离数据验证，不自动测试恢复到真实仓库。 |

这些演进方向应结合数据规模、故障证据和使用需求逐项评估。

## 验证范围

部署检查覆盖配置渲染、数据库初始化、角色配置和服务就绪。来源授权、模型效果与集群故障恢复分别在对应环境中验证。

开发与评审遵守[核心设计原则](core-design-principles.md)。
