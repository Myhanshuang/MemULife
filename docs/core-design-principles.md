# 核心设计原则

本文规定设计、开发、维护和代码评审的核心约束，适用于管理页面、导入流水线、核心服务、MCP、后台任务及数据维护工具。

新增功能、修复和重构都应保持这些约束。既有实现与原则不一致时，应记录并修复差异，不能把既有行为当作放宽约束的理由。原则调整须经维护者确认，并同步更新本文及相关协议。

本文规定设计边界，不代表所有历史数据和所有来源已经完成验收。功能与架构见[项目介绍](project-overview.md)，接口细节见[记忆修订协议](memory-revisions.md)。

## 1. 原始证据与整理结果分层

**原则：** 原始材料与对材料的理解分别保存，任何整理结果都应能追溯其依据。

- Source 保存来源材料，附件保留原件或可靠的来源引用；Detail 承担必要的中间整理；Unit 表达具体事件；日/月 Summary 和 Runtime 提供日期与主题层面的整体视角。
- 修正事件描述、主体、项目归属或全局认识时，修改相应 Unit 或视图，不能为了配合新结论改写 Source 原文。
- Unit 的证据引用与 Unit 之间的语义关系分开表达，不能把“相关”自动当作“证实”。
- 汇总、检索索引和目录服务于查找与理解，不能替代原始证据。自动主题应有跨来源、跨日期的证据，不能把每个出现的名称都变成长期主题。

**边界：** 用户明确删除来源片段或授权清理无意义材料时，可以移除对应内容；这是删除操作，不是重写原文。来源平台上的原件不因记忆系统内的删除而被删除。

## 2. 定位符、行号和引用必须稳定

**原则：** 已发布的地址是数据契约，修改和删除不能使其他记忆的引用错位。

- Unit 修订保持原定位符和记录起始行，正文增加换行也不能挤占后续记录的位置。
- 对按行定位的记录执行删除时，采用原位清空和删除标记，不压缩空行、不重排文件，不改变未涉及记录的字节与行号。
- 日/月 Summary 和 Runtime 使用稳定的条目 ID；正文内容、显示顺序和重新生成的文件行号不能充当条目身份。
- 修订不能把旧 ID 转给另一个事件；已删除条目不能因任务重放或索引重建而复活。

**边界：** 内部存储格式可以演进，但必须保持外部引用的含义和可解析性。格式迁移需说明兼容与恢复边界，不能通过重新编号解决迁移问题。

## 3. 模型负责理解，程序约束提交

**原则：** 允许外部模型利用更大的上下文修复局部记忆缺少全局视角的问题，由确定性的程序校验守住提交边界。

- 用户授权整理或修改后，外部模型可读取目标和证据，补充事件归属、关联不同实验、修正主体或整理主题，并直接提交最终改稿。
- 核心服务验证身份、权限、目标类型、版本、原文匹配和新增引用；直接修订不再交给内部模型二次解释或改写。
- 模型必须区分用户陈述、助手报告、实际执行结果和推断。工具调用不等于执行成功，助手宣称完成不等于已独立验证。
- 新增引用必须存在且类型正确；引用存在并不能证明其支持所写结论。模型仍需阅读证据，不得编造事件或依据。
- 修改理由用于解释和溯源，不充当权限凭证。外部模型不能提交任意 SQL、文件路径或内部导入控制指令来绕过校验。

**边界：** 授权修订不等于授予任意删除、清空或管理权限。自动提取与自动汇总继续在各自范围内工作，不能借这些任务覆盖已确认的手动改稿。

## 4. 所有修改使用统一的修订事务

**原则：** 管理页面和 MCP 使用同一套修订协议、校验和提交实现。

- 修改应提供目标定位符、目标的 `edit_revision`、原样 `old_text`、最终 `new_text`、修改理由和幂等键。视图条目还需提供稳定 `entry_id`。
- 原样摘录可以是局部内容，但必须精确且唯一匹配；不做模糊替换，不把文件版本当作条目编辑版本。
- 一批修改先完成所有目标与引用校验，再原子提交。任一冲突都不能留下半批修改；并发变化必须返回冲突，禁止静默覆盖。
- 冲突应返回当前内容与版本供重新判断。参数错误应明确指出字段或原因，不能只返回没有说明的错误码。
- 显式记录修改前后内容、调用身份、理由、时间、版本和事务编号。数据库事务保证原子性，版本历史必须另行保存；恢复旧内容也产生新修订。
- 相同身份、相同幂等键与相同参数重试，应返回同一结果；复用幂等键提交不同内容应拒绝。

**边界：** 正常导入与精确修订有不同输入规则。允许追加的操作应按协议声明，例如 Runtime 追加由程序分配新条目 ID；不能通过缺少定位信息的“修改”隐式新增内容。

## 5. 人工整理的内容默认受保护

**原则：** 用户或用户授权模型提交的整理成果，不能被后续自动流程覆盖。

- Unit、日/月 Summary 和 Runtime 修订默认标记为受保护；管理页面保存后明确显示保护状态。
- 自动汇总只能更新未保护部分，不能改写、删除或合并受保护条目的正文与引用，也不能撤销显式指定的主题归属。
- 自动重新导入或淘汰旧导入结果时，保留受保护 Unit 以及支撑其稳定引用的证据。
- 保护必须在服务端保存并在底层写入边界执行，与正文和历史一同持久提交；不能只在页面禁用按钮或内存中设置标记。
- 再次明确手动编辑受保护内容时，使用 `allow_protected=true`，仍校验版本和原文，保存后继续保护。只有显式 `protect=false` 才解除保护，自动任务不能自行解除。

**边界：** 保护防止自动覆盖，不阻止所有者明确执行删除。被删记录不能由保护快照恢复；受保护视图的证据被删除时，按下一条原则处理失效引用。

## 6. 删除必须处理完整的关联影响

**原则：** 删除是对内容及其依赖关系的一次一致性变更。

- 管理页删除 Unit 时，一并处理其直接关联的 Source 片段；删除 Source 时处理依赖该证据的记忆。
- 先计算并展示实际影响范围。共享证据可能影响其他 Unit，这些影响必须纳入范围，不能把关联删除伪装成只删一条。
- 只删除已确定范围内的内容，保留无关记录和行号。正文删除、删除标记与后台维护任务必须可靠关联。
- 相关旧索引和未保护的旧 Summary、Runtime 应失效或停止作为当前有效结果展示，并安排重建；不能让已删内容继续通过旧派生结果返回。
- 受保护视图中的原文和引用保持原样，失效引用明确标记，不继续当作有效证据或新的自动汇总依据。
- 区分删除连接配置、断开连接和删除记忆内容。删除过的来源不能显示成“已断开”；保留历史记忆时，如需展示来源状态，应准确标为来源已删除。

**边界：** 删除权限不能由修改权限隐式获得。来源平台原件、共享证据和已保留的手动内容分别按其授权范围处理，不能因为内部清理而扩大删除范围。

## 7. 持久提交后及时返回，重建进入后台

**原则：** 用户等待的是必要的持久提交，模型推理和派生数据维护由后台完成。

- 导入在素材和任务持久接收后返回；修改或删除在事务提交并可靠安排维护后返回，不把用户挂在等待汇总或向量重建的弹窗里。
- 索引、日/月 Summary、Runtime 和全局概览的维护进入持久队列，支持断点恢复和状态查询。队列不能仅存在于当前进程内存。
- 区分“已接收”“正文已提交”“派生数据待更新”等状态。汇总尚未完成或索引滞后，不等于写入失败。
- 后台任务发布结果前应核对输入版本和任务代次，拒绝过期结果覆盖较新的修改或删除。
- 网络中断导致结果未知时，使用原幂等键查询或重试，不能换键重复提交。重启后应恢复已提交任务，不重复生成已完成内容。

**边界：** 返回成功前仍须完成权限检查、冲突校验和持久化。不能以“后台处理”为理由提前报告成功，或把关键维护任务放进可能丢失的临时回调。

## 8. 保留有意义的记忆与正常附件

**原则：** 记忆管理展示有实际内容的记录，附件作为完整材料处理。

- 各来源统一过滤空正文、无有效事件的审计占位和纯自动上下文等无意义材料，不能只针对某一个来源或某一句固定文案处理。
- 在导入阶段阻止这些材料成为普通记忆；对已确认的无意义存量内容，执行清理，不能只靠前端隐藏让它们继续被检索和汇总。
- 内容判定必须结合正文、来源结构和附件，不能仅凭短文本或关键词删除有效材料。有真实附件但无正文的记录仍然可能有意义。
- 普通文件 Source 尽量按原件附件展示，适用于各种附件格式。内部解析可以用于提取记忆，页面不必把拆分结果当作多个原件展示。
- 来源资源具备可靠定位和按需读取能力时，媒体优先引用来源资源，避免为展示而默认下载原件；预览和原件访问分别处理。
- 预览失败或附件暂时取回失败必须如实显示，不能把“无法读取”判断成“没有有效内容”。清理过程中不得改写保留材料的原文和行号。

**边界：** 本地文件或需要保存原件的导入可在授权范围内保留附件。来源引用失效不意味着允许静默替换原件或清空记忆；应保留可追溯状态并反馈读取问题。

## 9. 管理界面围绕内容组织，交互保持统一

**原则：** 页面帮助用户选择、理解和维护内容，技术细节只在有助于操作时出现。

- 记忆导入与记忆管理分开。导入区处理接入、内容选择和导入记录；管理区处理来源记忆、日/月 Summary、记忆主题、搜索与维护。
- 接入配置尽量简化并复用来源能力。候选目录、展开操作、内容选择和预览在主内容区完成，左侧主要承担导航。
- 先预览和明确选择范围，再提交导入；连接成功不等于已经发现内容，也不等于完成导入。发现与预览不应提前形成正式记忆。
- Unit 列表突出正文，ID、证据来源、账户和 Source 等元数据放入详情。对话型 Source 按角色与顺序展示，文件型 Source 展示附件。
- 卡片随页面宽度自适应，宽屏两列、窄屏单列，高度按内容变化；新增入口、编辑器和筛选控件尽量复用现有组件与风格。
- 记忆管理的文字搜索使用明确的连续文字匹配，不做模糊搜索；范围可选 Unit、Source、Summary 和记忆主题。界面中的“记忆主题”对应内部 Runtime。
- 清理与用户操作无关的开发说明小字。保留必要的按钮、字段标签、保护标记、错误反馈、实际影响数量和刷新按钮旁的状态提示。

**边界：** 精确文字搜索不排斥系统另有明确区分的语义检索接口。简化页面不能隐藏错误、删除影响或内容是否真正保存等关键状态。

## 10. 验证适度，任务观察与操作可控

**原则：** 检查应针对本次变更的真实风险，提供足够证据后停止扩大验证。

- 只运行与改动直接相关的必要检查。涉及修订、删除、持久化时，重点验证行号与引用稳定、原子性、版本冲突、幂等、保护和后台一致性。
- 使用合成数据或隔离数据库验证写入与删除，不向真实记忆写入测试内容。部署验证优先使用只读操作。
- 文案和文档变更以内容、链接、格式检查为主，不为低风险改动运行完整测试套件。已有检查通过后，仅在新修改、失败或未解决疑点出现时补查。
- 对运行中的任务、实验、API 请求和后台进程，默认每 150 秒检查一次状态，相邻例行查询至少间隔 150 秒；优先使用完成通知或事件驱动等待，并保持能响应用户消息。
- 用户明确要求立即检查时可以立即查询。观察间隔不改变任务超时，不触发重复提交或自动重试。
- 日志保留排查所需的阶段、错误类别与关联编号，避免记录凭据和不必要的记忆正文。验收结论必须说明实际覆盖范围，不能把握手成功当作完整业务验证。

**边界：** “只做必要检查”不等于省略与数据完整性直接相关的验证，也不要求增加与本次改动无关的检查和审批流程。

## 需求冲突时的处理

| 场景 | 应遵守的取舍 |
|---|---|
| 自动汇总希望重写手动内容 | 保留受保护的正文、引用和条目身份，只更新未保护部分。 |
| 用户明确再次编辑受保护内容 | 校验当前版本与原文，记录新修订，继续保持保护。 |
| 用户明确删除受保护对象 | 按授权范围删除，不从保护记录中复活；更新相关依赖。 |
| 受保护汇总的证据被删除 | 保留汇总原文和原引用，明确标记失效，不冒充当前有效依据。 |
| 新内容与旧版本冲突 | 拒绝整批提交并返回当前状态，由调用者重新判断，不自动覆盖。 |
| 附件没有可读正文或预览失败 | 先区分正常附件、读取失败与真正的空占位，不能直接当作垃圾删除。 |
| 提交已完成，但索引或汇总未完成 | 及时返回已提交状态和维护状态，后台继续处理，不重新提交内容。 |
| 页面简洁与操作知情冲突 | 删除开发说明，保留实际影响、失败原因、保护和保存状态。 |

具体实施时，同时参照[记忆修订协议](memory-revisions.md)、[内容与证据规则](local-ai-content.md)、[可靠写入与恢复](reliability.md)和[采集端指南](acquisition.md)。
