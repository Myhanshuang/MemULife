# 存储、异步写入与恢复

## 数据边界

Markdown 和媒体文件保留正文。PostgreSQL 是目录、写入任务、视图调度、删除状态和索引的唯一在线控制存储；不使用 SQLite 存储这些数据。采集适配器读取第三方 SQLite 导出不受影响。

`memu_catalog` 保存小型目录记录，`memu_control` 按任务/状态项保存检查点。原始字节以内容哈希单份存放在 `.meta/source-originals/`；审计引用、消息布局等大 metadata 保存在 `.meta/material-metadata/` 的不可变文件中，以摘要地址引用。完成任务保留幂等指纹、来源定位符和结果，删除模型草稿与已处理向量。

首次打开旧库时，在取得独占服务锁后迁移 `catalog.tsv` 和 `maintenance.json`；旧文件随后冻结，不再读取或写入。`.meta/postgres.json` 绑定数据库身份。该标记存在而 PostgreSQL 控制记录缺失时拒绝启动，不能用冻结的旧 JSON 自动恢复在线状态。

备份必须同时包含 PostgreSQL 和完整记忆目录（含 `.meta`）。一致备份应暂停 core 写入后执行 `pg_dump -Fc` 并复制记忆目录。恢复时保留数据库的 repository_id 与目录标记。索引表可重建，控制表不能当作缓存丢弃。

## 写入协议

下述流程指默认 `mode=ingest`。外部模型直接修订使用 `mode=revise`，在一个事务中保存精确改稿、历史、保护状态和后台任务，立即返回提交结果；详见 [记忆修订协议](memory-revisions.md)。修订后的 Unit 使用新记录编码，起始行与其他记录行号不变；新版读取器同时识别旧文本记录与新编码，不能把含修订记录的仓库直接交给旧版读取器。

`memory_write` 将 Source、原始 metadata 和 queued 任务持久化后返回 `accepted`、`request_id`；HTTP 为 202。此时表示已接收，尚未完成模型整理。调用 `memory_status`（或核心 HTTP `POST /v1/tools/memory_status`）查询状态，传入原身份和 `request_id`。写入者只能查询自己的任务，所有者可查询所有任务。同一身份重用幂等键且材料一致时返回原任务；材料不同则冲突。导入投影采用来源实例、对象 ID 与原始哈希构成的固定幂等键；同一原件的高版本投影通过 `projection_updates` 持久替换，撤下旧派生内容并保留小型 `projection_receipts`，低版本重放不降级。

状态为 `queued → running → done`，可恢复错误进入 `waiting`，达到重试上限或无法恢复时进入 `failed`。响应包含阶段、尝试次数、下次时间和安全错误码。`done` 与 `index_ready` 分开：已提交的记忆不会因为索引暂不可用而重新生成。

Source 接收使用独立的四线程池，文件和控制记录提交仍受事务锁保护；不同写入任务可并发执行模型整理。采集前端区分接收素材和整理记忆。后台任务状态查询间隔至少 150 秒，每次 HTTP 请求最多查询 200 条回执。暂停采集阻止新的素材投递，已经持久接收的 core 任务继续完成。

`.env` 中 `MLLM_CONCURRENCY` 与 `EMB_CONCURRENCY` 分别限制 MLLM 任务和 embedding 调用并发，范围均为 1–32，默认均为 1；重启 core 生效。上限在整个核心进程内共享：视图整理也占用 MLLM 额度，语义查询也占用 embedding 额度。`EMB_THREADS` 仍是本地模型 CPU 线程数，与并发无关。HTTP / vLLM 后端允许并行调用；`local_gemma` 为保护单个本地模型仍在内部串行执行。

调度器最多保留两个并发额度之和的在途写入，推理期间释放写入锁，提交时重新取得锁并校验证据。相同 request_id 不会重复执行，会话延续按事件顺序提交。关系证据按块内容核验，同文件追加其他条目不导致冲突。独立的单线程索引发布器合并待更新文件，不占用模型任务槽位；投影替换等待在途写入结束。关停等待已启动任务完成，未同步的索引保留持久标记供重启后恢复，不重复生成模型产物。

持续接收且积压达到 `MEMU_SOURCE_PRIORITY_BACKLOG`（默认 32）时，优先保存 Source，暂停启动新的提取、编码和汇总任务；正在执行的任务完成后让出。连续 `MEMU_SOURCE_PRIORITY_QUIET_SECONDS`（默认 30 秒）没有新素材持久接收，或积压降到阈值以下，自动恢复派生处理。配置不会改变模型上下文预算。

模型提案校验失败最多修复两轮，保留原证据范围和读取配额；截断则把当前批次拆成两半并持久化拆分计划，最多六层。初始批量预算同时受输出 token 上限约束。资源不足、超时、限流和暂时不可用使用有上限的退避；同一个阶段的成功产物从检查点复用。

`MLLM_REPAIR_ATTEMPTS`、`MEMU_MAX_SPLIT_DEPTH` 可调整限额。调小这些值不会丢弃已接收的 Source。

## 文件与 SQL 一致性

先 fsync 待发布正文，再在同一 SQL 事务提交控制记录和文件发布意图，最后原子发布正文。每次进入仓库锁时先完成未发布意图。SQL 提交后的发布中断会在重启恢复，不重复调用模型；无法确认 SQL 提交结果时保留暂存字节。

## 索引和分页

按变更文件 revision 取出候选块，再按块内容和向量摘要增量 upsert；同一 Markdown 追加记录不会重写此前未变的块和向量。查询时从文件记录补入当前 revision。Unit 到原生媒体向量的事实关系在同步时物化，只刷新事实引用范围受影响的映射；关系邻居不会继承媒体向量。

后台写入在正文和向量检查点提交后即可完成，索引发布器合并这些变更。索引获取快照时短暂持有仓库锁，向量准备和 PostgreSQL 发布均不持有全局写入锁；发布完成只确认正文 revision、目录元数据、可见性及删除 epoch 都未变化的文件。发布期间新增的变更和向量继续保留为待同步，不把正常追加判为写入失败。删除与索引发布共用独立互斥锁，旧快照不能覆盖已完成的删除。索引出错会退避并暂缓新的派生任务，Source 仍可接收；持续接收达到压力阈值时，暂停启动下一轮索引发布。需要最新索引的关系检索仍同步等待并校验，普通查询在索引未就绪时明确返回未就绪。

Markdown 单次遍历为每个文件读取、解析一次，再直接定位块；后续读取复用有界缓存（最多 32 个文件，按原文总字节数限制为 8 MiB）。缓存根据文件身份、大小、纳秒级修改时间及事务暂存字节失效，覆盖追加、删除、回滚和外部编辑；返回的记录是独立副本，调用者修改结果不会污染缓存。超过缓存预算的文件在一次遍历内仍复用解析结果。正文的原子发布仍需写入变更文件，并未改为原地追加。

grep 使用 PostgreSQL 子串查询和 pg_trgm；语义检索在数据库内取有限 KNN 候选，再融合候选结果。语义候选窗口有上限，不声称枚举全库。

读游标使用请求文件的 revision；检索使用单调递增版本。视图刷新影响 grep 版本，通常不影响 Unit 语义检索版本。分页不读取媒体文件计算全库摘要。正文修改后旧游标会明确失效。

## 本地 AI 导入

只处理用户已选择的日志。按会话、代理分支、用户轮次合并，跨采集页保留末尾未完成轮次；长轮次分块保存原始审计，有界接续语义材料，结束后最多生成一个 Unit，不因整轮累计超过原来的 8 MiB 上限而中断批次。

Codex 原生 guardian/approval reviewer 会话在读取正文前排除。Codex 子代理和 Claude sidechain 的委派任务作为父代理背景，不能归属为用户或作为主证据；实际工作报告与工具结果仍可提取。已读完且未变化的文件不会在后续每页重新解压。

批量写入有就绪积压时，自动主题发现和视图汇总延后到写入队列排空，避免每处理少量记录就反复汇总。已完成 Unit 仍正常更新检索索引；所有者显式强制刷新不受此限制。汇总失败记录固定的校验错误类别，不记录模型输出或素材。

Claude Code、Codex、Gemini CLI、OpenCode 和 Cursor 共用带来源类型的事件层。自动压缩摘要、上下文重放和未知格式只存审计。区分用户原话、助手报告、工具调用和工具返回；后台通知不当作用户发言。成功的文件读取/导航/任务状态输出不生成独立工作成果。工具调用体（含文件内容与 diff）仅存审计，保留的工具结果有轮次条数与长度上限，原始内容完整保留。每个真实用户轮次最多一个最终 Unit；会话延续边按顺序直接生成，不调用关系模型。

模型提取目标、关键行动、可证实结果和未解决问题；无持久价值的运行事件允许不生成 Unit。每条摘要/Unit 必须引用精确主证据，程序核对其角色并使用事件观测时间；工具调用本身不能证明操作成功。助手报告保留未独立验证标签。仅审计和已替代的 Source 不参与普通检索。具体规则与边界见 [本地 AI 内容说明](local-ai-content.md)。

## 观测与验证

结构化事件仅记录 request_id、阶段、耗时、尝试次数、安全错误码等允许字段，不打印素材、模型提案或异常原文。`/readyz` 在存储不可用或模型未配置时返回 503，另报告 `index_ready`、`degraded` 和 `accepting_writes`。索引恢复期间保留持久接收能力；配置就绪不代表远端模型一定能成功执行。模型服务发现和索引恢复在后台执行，不阻塞 core 开始接收请求。

必要回归使用一次性 PostgreSQL 和合成模型故障，覆盖持久接收、发布恢复、资源退避、截断拆分、校验修复、增量索引和 Claude 跨页归并。日常修改不重复跑真实模型全链路。
